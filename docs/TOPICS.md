# 주제 선정

`topics/backlog.yaml`이 후보 풀이다. 이 문서는 **거기에 무엇을 넣고, 무엇을
빼고, 어떤 순서로 고르는지**를 정한다.

주제 선정은 자동화하지 않는다. 자동화하는 것은 후보를 모으고 상태를
추적하는 일뿐이고, 고르는 것은 끝까지 사람이 한다. 좋은 주제는 뉴스에 많이
나온 것이 아니라 지금 참가자가 고민할 가치가 있는 질문이기 때문이다.

## 뉴스가 유입, 지표가 검증

**주제는 뉴스에서 시작하고 지표에서 걸러진다.** 둘은 다른 질문에 답한다.

| | 답하는 질문 | 단독으로 쓰면 |
|---|---|---|
| 뉴스 | 무엇이 주의를 끌고 있나 | 가격에 후행하고, 프레임에 갇히고, 서사를 전달하게 된다 |
| 지표 | 무엇이 실제로 달라졌나 | 통계적 이상치를 찾을 뿐 아무도 궁금해하지 않는다 |

지표가 광범위해서 못 쓰겠다는 것은 **출발점으로 쓸 때만** 맞는 말이다.
834개 통계표에서 시작하면 무엇을 볼지 정할 수 없다. 검증 도구로 쓰면
범위를 뉴스가 정해준다. "장기금리 급등은 재정 때문"이라는 주장 하나를
받으면 볼 것은 커브와 발행량 둘뿐이고 5분이면 끝난다.

### 3단계

**1. 포착** — 읽다가 걸리는 것을 그 자리에서 던져 넣는다. 주 2~3건.

```bash
python3 cli.py topics capture \
  --headline "장기금리 급등, 재정 적자 우려 확산" \
  --claim   "국고 30년 금리 상승의 주된 원인은 국채 발행 증가다" \
  --source  "한국경제 2026-08-11" \
  --verify  "krx bond_kts 커브, 기재부 발행계획"
```

여기서 적는 것은 기사 요약이 아니라 **기사가 하는 검증 가능한 주장 하나**다.
"시장이 불안하다"는 주장이 아니라 분위기다. `--verify`를 채울 수 없으면
그 자리에서 버린다 — 탈락 조건 2에 이미 걸려 있다.

**2. 대조** — 회차를 정할 때 그 주장을 데이터로 확인한다. 결과는 셋 중 하나다.

| 결과 | 처리 |
|---|---|
| 주장 = 데이터 | 좋은 주제가 아니다. 확인하는 자리가 된다. "왜 그런가"로 한 단계 파면 살아난다 |
| **주장 ≠ 데이터** | **가장 좋은 주제다.** 간극 자체가 세션의 알맹이가 된다 |
| 확인 불가 | 탈락 |

지난 엔캐리 회차가 두 번째였다. 뉴스는 레버리지 펀드 청산을 말했는데
CFTC를 열어보니 롱·숏 합쳐 21만 계약으로 전체 미결제약정 41.9만의
절반뿐이었다. 서사가 시사하는 규모와 실제 포지션이 달랐고 그 간극이
세션이 됐다.

**3. 승격** — 살아남은 주장을 정식 후보로 만든다. 이때 축·질문·splits·
데이터·산출물을 채운다. 여기서부터 아래 규칙이 적용된다.

### 나머지 유입 경로

| 경로 | 내용 | 비중 |
|---|---|---|
| **뉴스·이슈 메모** | 운영자가 읽다가 걸린 것 | 주력 |
| **참가자 제안** | 카톡·워크시트로 들어온 것 | **주력이 되어야 한다** |
| 미해결 질문 | 지난 회차 Regime Note에 남은 것 | 보조 |
| 후속 질문 | 회차가 끝나며 갈라져 나온 것 | 보조 |
| 지표 스윕 | 분기 1회. 뉴스가 놓치는 느린 변화용 | 보완 |

지표 스윕을 분기 1회로 낮추되 없애지는 않는다. 인구, 부채 누적, 생산성
같은 것은 어느 날에도 뉴스가 되지 않지만 결국 가장 크게 작용한다.

**참가자 제안이 후보 풀에 들어오는 비율을 운영 지표로 본다.** 이 비율이
오르지 않으면 유입 경로를 뉴스로 바꿔도 여전히 운영자가 고른 주제를 잘
포장하는 시스템일 뿐이다.

### 자동 수집은 하지 않는다

뉴스 수집을 코드로 만들면 **많이 나온 것**이 올라온다. 그게 정확히 피하려던
것이다. 유지보수 비용도 실제 데이터 API보다 크다. 포착은 사람이 30초 쓰는
편이 낫다.

## 탈락 조건

하나라도 걸리면 후보에서 뺀다. 점수를 매기기 전에 먼저 거른다.

1. **결론이 이미 정해져 있다** — 찬반 어느 쪽도 진지하게 방어할 수 없다면
   토론이 아니라 확인이다
2. **데이터로 좁힐 수 없다** — 끝까지 인상과 의견만 오간다
3. **참가자 의사결정과 무관하다** — 알아두면 좋지만 내일 달라질 것이 없다
4. **6개월 안에 같은 질문을 다뤘다** — 새 데이터가 답을 바꿀 수 있을 때만 예외

## 정렬 기준

**위에서부터 순서대로 본다. 앞 기준에서 갈리면 뒤는 보지 않는다.**

1. 참가자가 **자기 기준을 문장으로 남기게 되는가**
2. 찬반이 **진짜로** 갈리는가
3. 지금이어야 하는 이유가 **데이터에** 있는가
4. 준비 비용이 감당되는가

가중치 합산 점수를 쓰지 않는 이유가 있다. 점수를 매기면 3번(시의성)이 높은
주제가 1번(산출물)이 낮아도 올라온다. 그게 정확히 뉴스 추종으로 가는 경로다.
사전식 정렬은 그 경로를 막는다. 1번에서 밀리면 아무리 시의적절해도 뒤로 간다.

## 배치 규칙

연 26회를 어떻게 나눌지의 문제다. 좋은 주제만 고르면 자연히 거시로 쏠린다.

- **같은 축 2회 연속 금지.** 1축은 특히 3회 연속하면 "그래서 뭘 하나"가 없이
  끝난다
- **4·5·6축을 분기 1회 이상.** 자기 포트폴리오·거래·성향을 다루는 축이
  목적함수에 가장 직접적이다. 데이터가 적다는 이유로 계속 밀리기 쉬우니
  달력에 먼저 박는다
- **3축(기업)은 1축 직후에.** 국면 판단 다음에 개별 기업이 오면 "그래서
  무엇을 사고 파는가"로 자연스럽게 이어진다
- **독서는 6~8주에 1회.** 시장이 조용할 때가 아니라 미리 정한 주기로 돌린다
- **1축은 분기 1회 이상.** 공통 좌표가 없으면 나머지 축의 대화가 흩어진다

## 후보 레코드

`topics/backlog.yaml`의 한 항목은 아래를 갖춘다. **결론 필드는 없다.**
후보 단계에서 답을 적기 시작하면 세션은 발표가 된다.

| 필드 | 내용 |
|---|---|
| `id` | `T-###` 주제, `B-###` 독서 |
| `axis` | 1~6 |
| `judgment` | 국면 / 비교 / 가치 / 리스크 / 타이밍 / 성향 |
| `title` | 한 줄 |
| `question` | **하나의** 질문. 예·아니오로 끝나지 않을 것 |
| `why_now` | 지금인 이유. 각 항목에 출처를 단다 |
| `splits` | 찬반이 갈리는 지점. 최소 2개 |
| `data.ready` | `full` 지금 뽑힌다 / `partial` 보강 필요 / `external` 밖에서 |
| `data.series` | 어느 소스의 무엇인지 |
| `output` | 참가자가 워크시트에 남기게 될 것 |
| `prep` | 예상 준비 시간 |
| `origin` | 유입 경로 |
| `status` | `candidate` / `selected` / `done` / `dropped` |

`status`가 `done`이 되면 그 회차의 Regime Note와 후속 질문이 새 후보를
만든다. 이 순환이 돌기 시작하면 후보 풀은 스스로 채워진다. 그 전까지는
지표 스캔과 참가자 제안으로 채운다.

## 검토 주기

회차가 끝난 다음 날 한 번. 30분이면 된다.

1. 방금 끝난 회차를 `done`으로 바꾸고 Regime Note를 링크한다
2. 워크시트의 "더 보고 싶은 것"을 후보로 옮긴다
3. 탈락 조건에 걸린 후보를 `dropped`로 내린다 — 쌓아두지 않는다
4. 배치 규칙을 보고 다음 회차 축을 정한 뒤, 그 축 안에서 정렬 기준으로 고른다

축을 먼저 정하고 그 안에서 고르는 순서가 중요하다. 반대로 하면 항상 1축이
이긴다.
