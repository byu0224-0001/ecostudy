# 03. 데이터 경로 — 공식 / 비공식

혼자 쓰는 도구에서는 **되는 경로를 겹쳐 두고, 하나 죽으면 다음을 쓴다.**  
공식만 고집하면 자막이 없고, 비공식만 고집하면 언제든 끊긴다.

상업 서비스로 올리지 않는다는 전제. 대량 수집, 프록시 돌리기, 우회 공격은 하지 않는다.

## 유튜브 — 필요한 능력 세 가지

| 능력 | 공식 | 개인용 보조 | 비고 |
|---|---|---|---|
| 키워드로 최근 영상 찾기 | Data API v3 `search.list` | InnerTube / yt-dlp 검색, Invidious | 공식이 쿼터에 약하다 |
| 제목·채널·날짜·길이 | Data API `videos.list`, oEmbed, RSS | yt-dlp metadata | 메타데이터는 비교적 쉽다 |
| 아무 영상의 자막 | **없음** (내 영상만 captions.download) | timedtext, youtube-transcript-api, yt-dlp | 이 제품의 핵심 병목 |

공식 API만으로는 “영상마다 의견 요약”이 성립하지 않는다. 자막이 막히기 때문이다.

### 공식: YouTube Data API v3

- 키 하나면 검색·메타데이터가 안정적이다
- 기본 쿼터 10,000 유닛/일
- `search.list` 1회 = 100 유닛 → **검색 약 100회/일**
- 혼자 쓰면 충분하다. 쿼리 확장 5번 × 하루 몇 키워드면 아직 남는다
- 결과는 알고리즘 편향이 있다. 다양성 규칙은 이쪽에 더 필요하다
- 채널 최신 영상은 API 없이 RSS로 된다  
  `https://www.youtube.com/feeds/videos.xml?channel_id=...`

전략: 검색은 공식 API를 **1순위**로 둔다. 키가 없거나 쿼터가 끝나면 비공식 검색으로 넘어간다.

### 비공식: 검색

개인 리서치용 보조.

1. **yt-dlp**  
   커뮤니티가 깨진 클라이언트를 가장 빨리 고친다. 검색, 메타, 자막을 한 도구로 처리할 수 있다.
2. **InnerTube (youtubei)**  
   앱이 쓰는 내부 API. 키 없이 검색이 된다. PO 토큰·데이터센터 IP 차단이 있다. 클라우드에서 돌리면 실패할 수 있다.
3. **Invidious / Piped 인스턴스**  
   공개 인스턴스 API로 검색·자막을 받는다. 인스턴스가 자주 죽는다. 본인 인스턴스를 띄우면 안정적이지만 운영 비용이 생긴다.

혼자 쓰는 순서:

```text
공식 search.list
  → 실패/쿼터 초과 시 yt-dlp 검색
  → 그래도 실패 시 지정 채널 RSS 폴백
```

지정 채널 RSS는 “다양성”과 반대처럼 보이지만, **내가 안 보던 채널 목록을 내가 직접 넣어 두는 폴백**이다. 알고리즘 대신 수동 화이트리스트.

### 비공식: 자막

의견 요약의 본진.

1. **youtube-transcript-api**  
   자동 생성 자막·수동 자막을 가져온다. 구현이 단순하다. 클라우드 IP에서 막히는 경우가 있다.
2. **yt-dlp `--write-auto-sub --skip-download`**  
   영상 파일 없이 자막만. 더 잘 버틴다. 쿠키가 필요해지는 시점이 온다.
3. **Invidious `/api/v1/captions/:id`**  
   인스턴스가 살아 있을 때만.
4. **후순위: 음성 → 텍스트 (Whisper)**  
   자막이 전혀 없을 때. 오디오를 받는 순간 ToS·용량·시간이 나빠진다.  
   1차에서는 **자막 없는 영상은 제목+설명만 약하게 표시하고 본문 요약에서 뺀다.**  
   Whisper는 “꼭 필요한 1~2개”만 수동 트리거.

주의:

- 자막은 캐시한다. 같은 영상을 두 번 치지 않는다
- 전문을 외부에 다시 올리지 않는다. 요약과 인용 문장만 보관
- 클라우드 IP가 막히면 **집 컴퓨터나 집 IP VPS**에서 자막만 돌리는 구성이 현실적이다
- residential 프록시 팜, IP 돌리기는 이 프로젝트 범위가 아니다

### 채널 다양성을 검색에 넣는 법

한 번의 `search.list`는 큰 채널을 돌려준다. 그래서 검색을 여러 번 쪼갠다.

```text
Q1  원문 키워드, order=date, 최근 14일
Q2  영문 동의어, order=date
Q3  원인 키워드 (발행, 재정, 터미널 프리미엄 …)
Q4  소형 채널 힌트: "해설", "개인투자", "macro"
```

그다음:

- videoId 중복 제거
- 채널당 1개
- 구독자 수는 `channels.list`로 받아 버킷에 넣는다 (공식, 유닛 저렴)
- 버킷에서 2:3:3으로 뽑는다
- 자막 가능한 영상을 우선한다

구독자 수를 비공식적으로 긁지 않아도 된다. 공식 API가 여기엔 싸게 잘 맞는다.

## 기사·칼럼

구글에 “공식 뉴스 검색 API”는 없다. 예전에 있던 News Search API는 폐기됐다.  
그래서 **한국어는 네이버, 영문·구글 느낌은 RSS + 검색 API**로 간다.

### 한국어 — 1순위 네이버 검색 API

- `GET /v1/search/news.json`
- Client ID / Secret
- 하루 25,000회. 혼자 쓰면 사실상 무한
- `sort=date`로 최신
- `originallink`가 원문, `link`가 네이버 뉴스
- `description`은 스니펫이다. 의견 추출에는 원문이 더 낫다

원문 추출:

- `trafilatura` 또는 `readability`로 본문만
- 실패하면 스니펫 + 제목으로 약하게 처리
- 페이월은 무리하지 않는다. “원문 못 읽음”으로 표시

네이버 블로그/카페 검색도 같은 검색 API 패밀리다.  
칼럼·개인 견해는 뉴스보다 여기 있는 경우가 있다.  
품질이 들쑥날쑥하니 **뉴스와 분리된 섹션**으로 두고, 본편과 섞지 않는다.

### 구글 쪽 — 공식에 가까운 무료

**Google News RSS** (키 없음):

```text
https://news.google.com/rss/search?q=미국+국채+금리+when:14d&hl=ko&gl=KR&ceid=KR:ko
https://news.google.com/rss/search?q=US+10-year+yield+when:14d&hl=en-US&gl=US&ceid=US:en
```

- 최근성 필터(`when:14d`)가 된다
- 제목, 링크, 발행일
- 구조화된 API가 아니고, 링크가 리다이렉트인 경우가 있다
- 본문은 없다 → 다시 원문 추출

**Google Custom Search JSON API**:

- 하루 100회 무료
- 사이트 제한을 걸면 “칼럼만” 검색이 된다  
  예: `site:hankyung.com OR site:mk.co.kr OR site:ft.com`
- 쿼터를 키워드 확장에 쓰면 금방 닳는다. 보조로만

### 영문·웹 검색 API (유료이나 개인은 저렴)

| 서비스 | 왜 쓰나 | 혼자 쓸 때 |
|---|---|---|
| Brave Search API | 뉴스 엔드포인트가 있다 | 무료 티어로 충분할 가능성 |
| Tavily | LLM이 먹기 좋은 청크 | 기사 종합에 잘 맞음 |
| SerpAPI | 구글 결과 그대로 | 비쌈. 필요 시만 |
| Exa / Perplexity Search | 의미 검색 | 칼럼 발굴에 좋음 |

1차 추천: **네이버 + Google News RSS + (선택) Brave 또는 Tavily 하나**.

SerpAPI로 구글 검색을 통째로 사오는 것은 비용 대비 이득이 작다.  
“구글링한 느낌”은 News RSS + 사이트 제한 검색으로 충분히 난다.

### 지정 RSS — 알고리즘을 우회하는 가장 정직한 방법

검색은 항상 누군가의 랭킹이다. 그래서 **내가 신뢰하는 매체 피드를 직접 받는다.**

예시:

- 한국: 한경, 매경, 서울경제, 연합인포맥스, 조선비즈
- 영문: Bloomberg(가능한 피드), FT, WSJ Opinion, Reuters, CNBC, Calculated Risk, 개인 서브스택
- 공공 1차: 기재부, 한은, 미 재무부, FOMC 캘린더

키워드로 거른다. 검색 API와 달리 랭킹 왜곡이 적다.  
다양성 버킷의 “1차 자료” 칸을 여기로 채운다.

### 비공식 기사 수집

개인 범위에서 현실적인 것:

- 사이트 검색 페이지를 직접 치는 스크레이프 — 깨지기 쉬움. RSS/API가 있을 땐 안 한다
- 네이버 뉴스 웹 HTML — 공식 API가 있으므로 불필요
- 페이월 우회, 아카이브 강제 열람 — 하지 않는다
- 뉴스레터 `.eml` 드롭 — 이전 프로젝트에서 이미 유효했다. **받는 메일만** 로컬에서 파싱하는 것은 합법적이다

뉴스레터는 통념 소스다. 원하면 2차에 `data/inbox/eml` 드롭 폴더를 다시 넣는다.

## 요약 모델

자막 8개 + 기사 8개는 토큰이 많다.

| 모델 | 장점 | 단점 |
|---|---|---|
| Gemini | 긴 컨텍스트, 저렴, 유튜브 URL 직접 이해 시도 | URL 직접은 불안정. 자막을 넣는 편이 낫다 |
| Claude | 주장 추출·갈림 정리에 강함 | 비용 |
| GPT | 무난 | 긴 자막 비용 |
| 로컬(Llama 등) | 유출 없음 | 품질·설정 |

추천:

- 개별 출처 요약: 싸고 빠른 모델 (Gemini Flash급)
- 의견 지도(합의/갈림): 좋은 모델 (Claude 또는 Gemini Pro)
- 숫자는 모델에게 계산시키지 않는다. 원문 숫자를 복사하게 하고, 없으면 “원문에 숫자 없음”

프롬프트 계약:

- 주장마다 `quote`(원문 짧은 인용)를 강제
- 인용을 코드가 원문에서 다시 찾는다. 없으면 그 주장을 버린다
- 이전 스터디 엔진의 `exact / fuzzy / missing` 아이디어는 여기 재사용 가치가 있다

## 캐시와 예절

개인이라도 상대 서버를 두들기지 않는다.

- 영상 메타·자막: videoId당 1회, 디스크 캐시
- 기사 원문: URL당 1회
- 동일 키워드 재검색: 30~60분 캐시
- 동시 요청 제한 (예: 유튜브 2, 기사 3)
- User-Agent를 정직하게, 필요하면 본인 키/쿠키만

## 추천 스택 (수집만)

```text
YouTube 검색     : Data API v3 → yt-dlp
YouTube 자막     : youtube-transcript-api → yt-dlp
YouTube 폴백     : 수동 채널 RSS 리스트
KR 뉴스          : 네이버 검색 API + trafilatura
글로벌 뉴스      : Google News RSS + Brave/Tavily
1차 자료         : 지정 RSS
칼럼/개인 견해   : 네이버 블로그 검색 (분리 섹션)
요약             : Gemini Flash + (지도는) Claude/Gemini Pro
저장             : SQLite
```

키가 아직 없어도 RSS + yt-dlp + 로컬 LLM으로 **빈 껍데기는 돌릴 수 있다.**  
키를 넣는 족족 품질만 올라가는 구조로 짠다.
