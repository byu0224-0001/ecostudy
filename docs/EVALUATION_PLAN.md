# 무엇을 어떻게 잴 것인가

## 지금까지 잰 것과 재지 않은 것

14통 전부 처리했고, 주장 489건이 나왔고, 사건 10건에 후보 4건이 나왔다.
이건 전부 **분량**이다. 파이프라인이 안 죽는다는 뜻이지 잘한다는 뜻이 아니다.

아직 아무도 모르는 것:

- 그 489건이 원문에 있는 말인가
- 하나의 사실을 다섯 조각으로 쪼갠 것은 아닌가
- 그 10건이 정말 각각 하나의 사건인가
- 그 4건 중에 실제로 열고 싶은 모임이 있는가

마지막 질문이 제일 중요한데 아직 답이 없다. 답이 없는 채로 모델을 Luna 로
올리면 "좋아 보인다" 말고 할 말이 없다. 비용을 두 배 쓸 근거가 안 된다.

그래서 지금은 만드는 것을 멈추고 자를 먼저 만든다.

## 사람이 필요 없는 점검부터

정답지는 손이 많이 든다. 그 전에 코드만으로 되는 것을 먼저 다 한다.
모델 호출도 없고 돈도 안 든다.

    python3 cli.py golden audit --llm

### 출처 대조

모델이 `source_span` 을 냈다고 그 구절이 원문에 있는 것은 아니다.
정규화한 블록 원문에서 직접 찾는다.

| 결과 | 뜻 | 인용 |
| --- | --- | --- |
| `exact` | 원문에 그대로 있다 | 가능 |
| `stitched` | 떨어진 두 곳을 `...` 로 이었다 | 불가 |
| `fuzzy` | 표현을 손댔다 | 불가 |
| `missing` | 원문에서 못 찾았다 | 불가 |
| `none` | 아예 안 냈다 | 불가 |

`stitched` 를 `fuzzy` 와 나눈 이유가 있다. 첫 실측에서 원문에 없던 8건은
지어낸 것이 아니라 대부분 떨어진 두 문장을 이어 붙인 것이었다. 조각은
각각 원문에 있으니 추적은 되지만, 그대로 옮기면 원문에 없는 문장이 된다.
성격이 다르니 따로 센다.

**목표는 `exact` 98% 이상**, 그리고 자료에는 `exact` 만 인용한다.

### 주장 밀도

블록 하나에서 몇 개를 뽑았나. 자카드 0.6 이상이면서 숫자까지 같으면
같은 말로 센다. 숫자가 다르면 문장 틀이 같아도 다른 사실이다
(코스피 6,579 와 코스닥 858 은 다른 사실이다).

봐야 할 것은 평균값보다 **분포**다. 특정 숫자에 몰려 있으면 프롬프트가
개수를 암시하고 있다는 뜻이다.

### 필드 판별력

한 값이 95% 이상을 차지하는 필드는 아무것도 가르지 못한다. 실제로
`researchable` 이 98% 참으로 나와서 없앴다. `verification_mode` 도
같은 기준으로 본다. 두세 종류로 쏠리면 이것도 다시 설계한다.

### 첫 측정 (2026-08-14, 14통)

| | 값 | 판단 |
| --- | ---: | --- |
| 주장 | 880 | 정답지 없이는 recall 개선인지 과추출인지 모른다 |
| 블록당 주장 | 5.27 (최대 18) | 특정 숫자에 몰린 봉우리는 사라짐 |
| `exact` | 99.9% | `stitched` 0, `missing` 0 |
| 유형 | 9종, 최다 26% | 가른다 |
| 검증 경로 | 5종, 최다 38.5% | 가른다. 옛 `researchable` 은 98% 한쪽이었다 |
| 사건 | 8건 (3~4개 매체, 여러 날) | |
| 사건 쌍 추측 | 66쌍 중 65쌍 `unrelated` | 사실상 한쪽으로만 찍는 중 |

마지막 줄이 지금 가장 정직한 신호다. 휴리스틱이 거의 전부 `unrelated`
라고 답하고 있으므로, 정답지의 `unrelated` 비율이 높으면 정확도가 저절로
높게 나온다. 그래서 전체 정확도가 아니라 라벨별 재현율을 봐야 한다.

`SAME` 0.35, `RELATED` 0.10 두 문턱은 **지금 근거가 없다.** 눈으로 보고
정한 값이다. 정답지가 생기면 그때 맞춘다. 지금 손으로 맞추면 표본 몇 개에
과적합할 뿐이다.

## 정답지

    python3 cli.py golden seed all --llm      # 표본 뽑기
    python3 cli.py golden status              # 어디까지 채웠나
    python3 cli.py golden score               # 채점

`data/golden/dev/*.jsonl` 에 한 줄씩 들어간다. `label` 이 비어 있으면
채점에서 빠지므로, 확신이 없는 줄은 비워 두는 편이 낫다. 애매한 판정을
억지로 채우면 자가 휘어진다.

표본은 분류마다 골고루 뽑는다. 앞에서 그냥 자르면 흔한 분류만 들어가고
드문 분류가 빠지는데, 틀리는 건 대개 드문 쪽이다.

### 다섯 계층, 이 순서로

| 계층 | 수량 | 사람이 정하는 것 |
| --- | ---: | --- |
| 주장 쓸모 | 100 | keep_core / keep_supporting / drop_* |
| 주장 빠짐 | 20블록 | 뽑혔어야 하는데 빠진 것 |
| 블록 분류 | 80 | lead / brief / sponsored / self_promo / ui_residue ... |
| 주장 쌍 | 80 | same_event / related_theme / unrelated |
| 주제 | 15 | 다섯 기준 각각 통과 여부 |

**주장부터다.** 사건은 주장을 재료로 만들어진다. 재료가 성한지 모르는 채로
요리 맛을 평가하면, 맛이 없을 때 재료 탓인지 조리 탓인지 알 수 없다.

### 맞는 주장과 필요한 주장은 다르다

"코스닥이 7% 올랐다"는 유형도 맞고 원문에도 있다. 그런데 그 글의 요지가
"기관 수급과 정책 기대가 겹쳐 급등했다"라면, 이 주장 하나만으로는
리서치에 쓸 게 없다.

주장 추출의 목표는 모든 사실을 빠짐없이 옮기는 것이 아니라 **뒤 단계에
필요한 것만 남기는 것**이다. 그래서 맞았나/틀렸나가 아니라 남길까/버릴까를
묻는다.

    keep_core          요지를 이룬다
    keep_supporting    근거로 필요하다
    drop_background    맞지만 각주다
    drop_redundant     다른 주장과 같다
    drop_invalid       잘못 뽑았다

### 뽑은 것만 보면 절반만 보는 것이다

주장 100개에 전부 라벨을 붙여도 **빠진 것은 한 건도 안 세어진다.** 아예
안 뽑힌 주장에는 붙일 라벨이 없기 때문이다.

그래서 블록 20개를 통째로 읽고 무엇이 빠졌는지 적는 층을 따로 둔다.
이게 없으면 880이 과추출인지 recall 개선인지 영영 못 가른다.

    뽑은 것의 질   claims 의 utility
    놓친 것의 양   recall 의 missed

### 찾기와 판정은 다른 일이다

사건 관계를 맞히는 일은 두 단계다.

    찾기(retrieval)     비교해 볼 만한 쌍을 골라 올린다
    판정(adjudication)  올라온 쌍이 같은 사건인지 정한다

**이 둘을 한 숫자로 보면 안 된다.** 찾기가 진짜 같은 사건인 쌍을 아예 안
올리면 판정이 아무리 똑똑해도 소용없다. 그 쌍은 판정자에게 도착조차 하지
않는다. 나중에 "Luna 가 왜 이걸 놓쳤지" 할 때 사실은 앞 단계 문제인 경우를
가려내려면 따로 재야 한다.

    찾기   재현율 — 실제 양성 중 몇 쌍이나 올렸나
    판정   분류별 정밀도·재현율·F1

정답지의 `retrieved` 가 기계가 올렸는지 여부이고, `label` 이 사람 답이다.
둘이 어긋나는 지점이 곧 고칠 곳이다. 그래서 기계가 **안 올린** 쌍도 표본에
일부러 섞는다. 올린 쌍만 라벨링하면 찾기 재현율은 정의상 100%가 된다.

### 사건이 아니라 주장끼리 짝짓는 이유

처음에는 사건끼리 짝지었다. 단위가 틀렸다. 묶는 일을 이미 끝낸 결과물끼리
비교하는 것이라 같은 사건인 쌍이 나올 수가 없다. 실제로 12개 사건에서
66쌍을 만들었더니 56쌍이 아예 겹치는 단어가 없었다.

판정해야 할 것은 두 **주장**이 한 사건인가다. 묶는 기계가 답하는 질문이
바로 그것이기 때문이다.

- 코스닥 기관 순매수 ↔ 코스닥 7% 상승 → `same_event`
- 엔비디아 AI 투자 ↔ 삼성전자 HBM 공급 → `related_theme`
- 미국 CPI ↔ 국민연금 국내주식 → `unrelated`

### 쏠린 표본으로는 아무것도 못 잰다

문제 66개 중 65개의 답이 같으면 전부 그 답으로 찍어도 98점이 나온다.
처음 만든 사건 쌍 세트가 정확히 그랬다.

다만 **정답 분포를 미리 맞출 수는 없다.** 정답을 아직 모르기 때문이다.
할 수 있는 것은 겹침이라는 연속값을 여섯 구간으로 나눠 고르게 담는
것뿐이다. 한 바퀴 라벨을 붙이고 나면 그때 진짜 분포를 보고 다시 뽑는다.

어려운 쌍을 일부러 넣었다. "코스피 6,813.34 상승"과 "코스피 6,579.04
상승"은 단어가 100% 겹치지만 다른 날의 다른 마감이다. 글자만 보는 방법은
여기서 반드시 틀린다.

### 주제 다섯 기준

각각 0/1 로 매긴다. 다섯 개 다 통과한 것만 실제로 열 수 있는 후보다.

| 기준 | 묻는 것 |
| --- | --- |
| `why_now` | 지난달에 해도 됐을 얘기 아닌가 |
| `investment_link` | 결국 무엇을 사고 팔지에 닿는가 |
| `debatable` | 답이 정해져 있으면 두 시간이 안 간다 |
| `standalone` | 앞뒤 회차 없이 그날 하루로 성립하는가 |
| `evidence_ready` | 확인할 자료에 실제로 닿을 수 있는가 |

## 개발용과 시험용

지금 14통은 프롬프트를 고치고 스키마를 두 번 갈아엎는 동안 계속 봐 왔다.
이 메일들에 맞춰 시스템을 손댔으니 **여기서 잘 나오는 건 당연하다.**
이걸로 낸 숫자를 성적표라고 부르면 안 된다.

    dev       현재 14통. 고치면서 계속 본다.
    holdout   앞으로 올 5~10통. 끝까지 안 본다.

`golden seed --split holdout` 은 막아 두었다. 한 번 열면 그 순간 dev 가
되고 되돌릴 수 없다. 마지막에 딱 한 번 돌려서 dev 와 얼마나 차이 나는지
본다. 차이가 크면 14통에 과적합한 것이다.

## 무엇과 무엇을 비교하나

정답지가 생기면 같은 세트에 세 가지를 돌린다.

| | 사건 쌍 정확도 | 호출 | 토큰 | 비용 | 지연 |
| --- | --- | --- | --- | --- | --- |
| 지금 휴리스틱 | | 0 | 0 | $0 | |
| Luna 판정 | | | | | |
| Terra 판정 | | | | | |

정확도만 보면 안 된다. Terra 가 3%p 더 맞히는데 비용이 여섯 배면 안 쓰는
게 맞다. 그래서 호출·토큰·비용·지연을 같이 기록한다.

    python3 cli.py topics mail --llm --cost

캐시가 있으면 2초에 끝나지만 그건 오늘 안 낸 돈일 뿐이다. 매일 아침 오는
새 메일은 전부 실호출이다. **운영 비용은 cold 기준으로만 본다.**

### 첫 cold 측정 (14통 전량, 캐시 0)

| 단계 | 모델 | 호출 | 입력 | 출력 | 비용 |
| --- | --- | ---: | ---: | ---: | ---: |
| 블록 분류 | Nano | 14 | 96,807 | 12,433 | $0.035 |
| 주장 추출 | Luna | 197 | 400,157 | 181,509 | $1.489 |
| | | **211** | | | **$1.524** |

32분 걸렸다.

**이 표가 앞선 계획 하나를 뒤집는다.** Nano·Luna·Terra 3단 라우팅은 분류가
호출의 대부분이니 거기를 싸게 만들자는 생각이었다. 실제로는 분류가 전체
비용의 **2.3%** 다. 블록 분류를 공짜로 만들어도 청구서는 그대로다.

돈은 전부 주장 추출에 있다. 호출 197건, Luna. 줄일 방법은 셋인데 순서가
있다.

1. **보내는 블록을 줄인다.** 지금 167블록 중 몇 개가 쓸모없는지 모른다.
   정답지의 블록 분류 성적이 나오면 안전하게 걸러낼 수 있는 양이 보인다.
2. **추출을 Nano 로 내려 본다.** 정답지로 Luna 와 붙여 보고 차이가 작으면
   내린다. 재 보기 전에는 못 내린다.
3. **Batch API.** 아침 브리핑은 실시간일 필요가 없다. 반값이다.

셋 다 정답지가 먼저다. 지금 내리면 얼마나 나빠지는지 모른 채 내리는 것이다.

32분도 문제다. 호출당 9초씩 순차로 돈다. 매일 아침 쓰려면 동시 실행이나
Batch 가 필요하다. 다만 이건 정확도와 무관하니 나중에 해도 된다.

## 매체 수를 세는 방식에 남은 문제

뉴스레터 세 곳이 같은 사건을 다뤘다고 근거가 셋인 것은 아니다. 셋 다 같은
로이터 기사를 옮겨 쓴 것일 수 있다. 그러면 실제 독립 근거는 하나다.

지금 `source_count` 는 뉴스레터 수를 센다. 이걸 근거의 다양성이라고 부르면
안 된다. 제대로 하려면 원 출처를 따로 뽑아야 한다.

    newsletter_source   DailyByte
    underlying_source   Reuters

지금 당장 만들지는 않는다. 다만 `source_count` 를 confidence 의 재료로만
쓰고 근거 수로 부르지 않는다. 정답지를 만들 때 원 출처가 같은 쌍이 보이면
`note` 에 적어 둔다. 나중에 이 계층을 만들 때의 재료가 된다.

## 정답은 사람만 쓴다

표본을 고르는 데는 코드도 모델도 써도 된다. 정답은 아니다.

모델이 붙인 라벨을 정답으로 저장하고 그 모델을 채점하면 자기 답안지로
자기를 채점하는 셈이다. Luna 가 만든 라벨로 Luna 를 재면 당연히 잘 나온다.

`golden seed` 는 저장할 때 답안 칸(`label` `utility` `label_mode` `atomic`
`criteria`)을 한 번 더 비운다. `--llm` 은 **평가받을 결과물을 만드는**
플래그이지 정답을 만드는 플래그가 아니다.

## 순서

1. 자동 점검 — 출처 대조, 주장 밀도, 필드 판별력 ✔
2. **주장 쓸모 100건** — 880 중 몇 개가 필요했나
3. **주장 빠짐 20블록** — 무엇을 놓쳤나
4. 프롬프트 재조정 → 2·3번 다시 측정
5. 주장 쌍 80건 — 찾기 재현율과 판정 F1 을 따로
6. 사건 후보 생성 개선
7. Luna 판정 붙이고 5번과 비교. Terra 는 Luna 로 부족할 때만
8. 주제 품질 15건

10. 여기까지 통과하면 V0 완료
