# 06. 세 의견 비교와 최종 결정

세 의견은 같은 제품을 가리킨다. 품질 차이는 **무엇을 제품으로 보느냐**에서 난다.

| | 의견 A (장문) | 의견 B (MCP·파이썬·n8n) | 의견 C (바이브 코딩) | 이 저장소의 이전 설계 |
|---|---|---|---|---|
| 제품의 핵 | 논점 충돌 지도 | 다관점 요약표 | 주장-근거-전제 JSON | 필터 버블을 깨는 의견 지도 |
| 1차 구현 | n8n + SerpApi + Supabase | MCP를 가장 추천, 파이썬은 차선 | 파이썬 + Pydantic | 텔레그램 봇 + 파이썬 엔진 |
| 자막 | Supadata/Apify 또는 라이브러리 | `youtube-transcript-api`, 실패 시 Whisper | 실패하면 스킵 | 라이브러리 → yt-dlp, Whisper는 나중 |
| 기사 | SerpApi 한 업체 | Tavily | Tavily | 네이버 + Google News RSS |
| 폰 | Streamlit을 언급, 폰은 약함 | 노션/텔레그램은 부가 | CLI 먼저 | 폰이 도착점 |

의견 B는 본문이 두 번 반복돼 있다. 새로운 설계는 없고, 의견 A·C와 충돌하는 추천(MCP 최우선, 강세/약세 이분, 영상 5개)이 들어 있다.

## 취할 것

**의견 A에서.**

- 제품 문장은 “요약해 준다”가 아니라 **놓친 관점을 찾아 준다**다.
- 영상별 상승/하락 라벨로 끝내면 쓸모가 없다. 단위는 논점이다.
- 한 출처 안에서도 문장을 나눈다. 사실 / 해석 / 의견 / 전망 / 그 출처가 말하는 투자 함의.
- 수집은 넓게, 분석은 Map-Reduce. 자막 원문 20개를 한 프롬프트에 넣지 않는다.
- 검색어를 일부러 가른다. 원문, 영문, 상승 프레임, 하락 프레임.
- 전망 필드를 지금 저장하면, 나중에 “그때 말이 맞았나”를 붙일 수 있다.
- Gemini와 NotebookLM은 **오늘 손으로 프롬프트를 시험하는 도구**다. 시스템 구성 요소가 아니다.
- MCP는 엔진이 생긴 뒤의 얇은 어댑터다.

**의견 B에서.**

- Map 단계에서 출처마다 뽑고, Reduce에서 비교표를 만든다는 순서.
- 자막 없는 영상은 파이프라인을 멈추지 않는다.

**의견 C에서.**

- n8n은 이 문제의 본체가 되기엔 약하다. 정형 JSON, 인용 검증, 다양성 선별은 코드가 맞다.
- 스키마를 먼저 고정하고, 모델은 그 틀로만 답하게 한다.
- 1차는 CLI에서 텍스트가 나오는 것. 다만 읽는 화면은 CLI가 아니다.

**이전 설계에서 유지.**

- 엔진과 창구를 분리한다.
- 채널당 1개, 조회수순 금지, 구독자 크기 버킷.
- 인용문은 코드가 원문에서 다시 찾는다. 없으면 그 주장을 버린다.
- 공식 자막 API는 남이 만든 영상에 쓸 수 없다.
- 페이월 우회, 프록시 팜, 대량 수집은 하지 않는다.
- 혼자 쓴다. 다사용자·결제·앱스토어는 하지 않는다.

## 버릴 것

**n8n을 MVP의 본체로 두지 않는다.** 의견 A의 1차 추천은 여기서 틀린다. 수집 노드를 잇는 데는 빠르고, 20개 출처를 스키마로 맞추고 같은 명제끼리만 충돌시키는 데는 느리다. 알람이나 텔레그램 발송을 나중에 맡길 수는 있다.

**MCP를 가장 먼저 만들지 않는다.** 의견 B의 최우선 추천은 세 의견 중 가장 약하다. MCP는 모델이 도구를 고르게 둔다. 다양성 선별은 모델이 빠뜨려도 되는 단계가 아니다. 코드가 8개를 고른 뒤에야 모델이 분석한다. Cursor에서 `brief` 한 번 치는 포장으로 MCP를 붙이는 것은 4단계다.

**SerpApi를 기본 수집기로 두지 않는다.** 구글 뉴스·구글 검색·유튜브 검색을 한 청구서로 묶는 편의는 있다. 자막은 해결하지 못하고, 한국어 기사는 네이버가 더 맞고, 개인 사용량에서는 Google News RSS가 공짜다. SerpApi는 키가 있고 RSS가 부족할 때의 스위치다.

**Supadata·Apify를 기본 자막 경로로 두지 않는다.** 개인 도구가 자막을 제3자에게 맡길 이유가 1차에는 없다. `youtube-transcript-api` 다음 `yt-dlp`. 클라우드 IP가 막히면 집 워커. 유료 자막 API는 그 다음이다.

**`youtube-search-python`을 검색 본체로 두지 않는다.** 공식 Data API와 `yt-dlp`가 유지보수 측면에서 위에 있다. 의견 C의 검색 라이브러리 지정은 채택하지 않는다.

**Streamlit을 읽는 화면으로 두지 않는다.** 폰에서 썸네일, 논점, 타임스탬프를 읽기 나쁘다. 이 저장소의 읽는 화면은 이 디자인의 HTML 리포트다.

**강세/약세 이분과 “영상 5 + 기사 5”를 성공 기준으로 두지 않는다.** 의견 B의 프롬프트 예시는 의견 A가 쓸모없다고 한 출력이다.

**Whisper를 1차 예외 처리로 넣지 않는다.** 오디오를 받는 순간 시간, 용량, 저작권 부담이 커진다. 자막 실패는 건너뛴다. 개수는 “자막 있는 영상만 N개”로 센다.

**Gemini의 유튜브 URL 이해를 파이프라인에 넣지 않는다.** 검색 몇 개로 답하는 데 쓸 수 있다. 재현 가능한 데이터셋은 되지 않는다. NotebookLM은 모아 둔 URL을 시험 분석할 때 쓴다. 수집기가 아니다.

**시청 기록을 자동으로 읽는 기능은 없다.** “평소 채널과 72% 유사”는 매력 있지만 YouTube Data API는 남의 시청 기록을 주지 않는다. 2차에 사용자가 채널 목록을 직접 넣는다. 클릭한 카드로 그 목록을 채운다.

**pgvector는 지금 필요 없다.** 출처는 한 번에 수십 개다. SQLite면 된다.

**모델 신뢰도 점수를 내지 않는다.** “확신 0.83”은 검증이 아니다. 검증은 인용 매칭, 타임스탬프, 1차 자료 여부다.

## 환각에 대한 한 가지 수정

의견 A·C의 모순 지도는 맞다. 그대로 두면 모델이 **없는 논쟁을 만들어** 낸다. 두 사람이 다른 명제를 말하고 있어도 “상승 vs 하락”으로 붙이기 쉽다.

Reduce 규칙:

- 같은 명제에, 양쪽 모두 원문 인용이 있을 때만 쟁점으로 올린다.
- 아니면 `비교 불가`로 두고, 어느 쪽 말이 비었는지 적는다.
- 투자 함의는 **그 출처의 말**이다. 시스템의 매수·매도 의견이 아니다.

## 개수

후보 30~50개를 모으되, 읽는 카드는 **영상 8, 기사 6**을 기본으로 한다. 폰에서 20장 요약을 읽지 않는다. 화면은 “후보 36개 중 채널·언어·논점 기준으로 8개”를 보여 준다. 나머지는 접어 둔다.

자막 분석 비용은 이 8개에만 쓴다. 다양성 선별이 분석보다 먼저다.

## 최종 형태

```text
폰에서 키워드
    → 텔레그램 (트리거, 알림, 짧은 한 줄)
    → 리포트 페이지 (읽는 화면)
         쟁점 지도
         영상 카드: 썸네일, 원제목, 키워드, 의견, 다른 점, 타임스탬프
         기사 카드

엔진은 파이썬.
스키마는 Pydantic.
저장은 SQLite.
MCP / n8n / Whisper / 전망 채점 / 시청 채널 목록은 순서가 나중이다.
```

텔레그램을 본편 UI로 두었던 이전 결정은 여기서 바뀐다. 썸네일과 논점 표는 메시지에 안 들어간다. **텔레그램은 리모컨, 리포트가 본편**이다.

## 진행 순서

1. 이 문서의 스키마와 리포트 시안을 고정한다. 시안은 샘플 데이터다.
2. CLI가 같은 JSON을 만든다. 키가 없으면 빈 소스는 건너뛴다.
3. JSON을 이 HTML에 넣는다.
4. 텔레그램은 완료 링크만 보낸다.
5. 인용 매칭이 된 뒤에만 쟁점 지도를 신뢰한다.
